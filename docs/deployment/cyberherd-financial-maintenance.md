# First financial configuration transaction

`activate-cyberherd-financial.py` consumes the
[financial candidate](cyberherd-financial-stage.md) and a separately reviewed,
completed [six-program upgrade](cyberherd-program-maintenance.md). It changes four
configuration files, with distinct plan, stopped-writer checkpoint, application,
financial resumption and pre-resumption configuration rollback operations. The
authenticated root tool closure now contains **27 files**. Authenticate the
root-owned launcher externally before isolated interpretation; never execute a
writable checkout as root.

This is the first transition from zero financial ceilings and masked outgoing
roles. It is not a general budget-update or financial recovery tool. Its source
does not establish production installation, provider execution or activation.
The full twelve-part port remains incomplete.

## Sealed inputs and plan

All six limits must already be explicitly chosen and match the actual stored
member allocation. The candidate's four exact configurations, unchanged originals,
native checker and cross-role UID/socket/owner/epoch/account bindings are rechecked.
The completed program review is read as private data under its independently
selected digest. Its selected six program hashes must match the current installed
programs and original financial identity; original-program rollback/resumption
does not qualify. No older tool code is interpreted from that review.

The new plan preserves installed programs, configuration, credentials, units,
payees/aliases, private-contact/self-read/operator settings, template/publication
choices and physical controls. It stages only four exact configuration replacements,
retaining original metadata/labels, all original protected files and the native
verifier. The four-role checker and all three installed worker parsers must accept
the candidates under their original runtime UIDs, isolated networking, cleared
groups/capabilities and NoNewPrivileges. No runtime, journal or credential opens.

Launcher argument shapes:

```text
--cyberherd-financial-maintenance plan
  CANDIDATE_REVIEW COMPLETED_PROGRAM_REVIEW NEW_TRANSACTION
  --candidate-sha256 CANDIDATE_SHA256 --program-review-sha256 PROGRAM_REVIEW_SHA256

--cyberherd-financial-maintenance checkpoint NEW_TRANSACTION
  --review-sha256 TRANSACTION_SHA256 --exclusive-maintenance
```

These are argument shapes, not production commands or activation approval.
The private plan's `PREPARED.json` digest must be independently selected before
maintenance. Checkpoint requires an explicit exclusive maintenance window. It
rechecks the original running installation and selected stored allocation before
stopping core/member and requiring all four writers masked, inactive and absent
from their cgroups and runtime UIDs. It accepts a fresh native four-journal backup
and creates a separate native reward review bound to that exact image set, owner
and epoch. `CHECKPOINT.json` and `reward-review/REVIEW.json` remain private.
Checkpoint changes no configuration and starts no service.

## Historical work and application

Native review now counts unreceived `payment_received` and `feeder_confirmed`
events beyond the membership cursor separately from an ordinary informational
cursor gap. Missing counters from an older reader fail closed. First application
requires zero unreceived payment/feeding events, zero pending feeding inputs,
no unfinalized core reservations, unresolved provider submissions or payout holds,
and the chosen stored allocation. Deferred social/payment intake and unresolved
physical work remain visible and preserved; they confer no new payout authority.

Unplanned funded positive-allocation barriers, awaiting reservations and reserved
plans require a separate accounting decision. The transaction never retrofunds,
replans, closes or deletes them. Frozen zero/unfunded barriers and existing
`no_payout` plans remain under their existing native semantics. Today's percentage
cannot rewrite a historical snapshot. Ordinary overlay/weather cursor lag alone
does not block the transaction.

```text
--cyberherd-financial-maintenance apply NEW_TRANSACTION
  --review-sha256 TRANSACTION_SHA256 --checkpoint-sha256 CHECKPOINT_SHA256
  --reward-review-sha256 REWARD_REVIEW_SHA256 --exclusive-maintenance
```

The exact checkpoint/report digests are independent operator input. Application
revalidates the accepted native backup, original live-image fingerprints, selected
programs and native configuration checks, then replaces only the four configuration
files while all writers remain stopped/masked. Journals, signed bytes, credentials,
units and program files are never restored or migrated. Partial application retains
the transaction and masks instead of guessing a new backup or repeating a start.

## Financial resumption and honest qualification

```text
--cyberherd-financial-maintenance resume NEW_TRANSACTION
  --review-sha256 TRANSACTION_SHA256 --checkpoint-sha256 CHECKPOINT_SHA256
  --reward-review-sha256 REWARD_REVIEW_SHA256
  --approve-financial-activation --acknowledge-provider-recipient-review
```

The last flag records the operator's completed credential/provider-readiness and
intended-recipient review. It is an **operator attestation**, not a provider probe
or proof that quote execution, recipient payment or receipt publication succeeded.
Never supply it on a live host merely because configuration/CI checks pass. A
controlled quote/execute/payment observation remains part of supervised financial
acceptance. The result explicitly keeps `provider_execution_qualified=false` and
`external_recovery_adopted=false`; the native report's external-reconciliation
requirement remains intact. No recovery marker or financial hold is cleared.

Resumption repeats all fresh-backup, unchanged-image, financial-tail, frozen-work,
native-parser and installed-code checks. A durable resumption fence precedes any
unmask/start or persistent enablement. Effective units, identities and every active
override must match the frozen installation. It restores core/member and unmasks,
enables and starts the separate signer/payout roles, checking their exact vendor
enablement links and running executable identities. Core/member local health is
checked. Original core/member boot behavior is preserved. The coordinator issues
no provider/signing/feeder RPC, but approved workers can subsequently perform
bounded payouts/signatures and resume the existing feeder path. Existing override,
UUID ambiguity and household safety controls remain authoritative.

Once this fence exists, automatic rollback or another start attempt is refused:
workers may already have written original claims, signed bytes or provider outcomes.
Inspect a failed/partial start and reconcile under the retained identities instead
of deleting markers, changing IDs or restoring an earlier database.

## Before any resumption

```text
--cyberherd-financial-maintenance rollback NEW_TRANSACTION
  --review-sha256 TRANSACTION_SHA256 --checkpoint-sha256 CHECKPOINT_SHA256
  --reward-review-sha256 REWARD_REVIEW_SHA256 --approve-configuration-rollback

--cyberherd-financial-maintenance resume-original NEW_TRANSACTION
  --review-sha256 TRANSACTION_SHA256 --checkpoint-sha256 CHECKPOINT_SHA256
  --reward-review-sha256 REWARD_REVIEW_SHA256 --approve-original-resumption
```

Before the resumption fence only, rollback verifies the accepted backup and exact
unchanged originals, then restores just the four configuration files. It never
restores a journal. A separate original-resumption command starts only core/member
and retains masked outgoing roles and zero financial ceilings. Financial resumption
is refused once rollback was selected. Failed checkpoint verification without an
accepted checkpoint requires inspection rather than an invented recovery grant.

## Qualification scope

Protected-file fixtures cover actual four-file replacement, original metadata,
partial-application rollback, financial-image drift, missing financial-tail fields,
funded backlog, qualified-program identity, explicit acknowledgment and start fences.
Native synthetic tests distinguish financial versus informational cursor tails at
the exact cursor. The disposable installed rehearsal additionally exercises actual
native backup/review/configuration application and four systemd services using
synthetic credentials, selected nonzero caps and a signing-helper trap. Its network
contains only loopback and its original unknown feeder UUID is preserved. It does
not establish production provider/recipient, real signature or payment acceptance.
