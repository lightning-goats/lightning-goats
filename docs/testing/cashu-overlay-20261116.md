# Cashu overlay development checkpoint — 2026-11-16

The frontend adds an upper-left Cashu request QR, keeps the canonical branded
Lightning QR at its original upper-right coordinates, moves the status/price
strip to the top center, and moves the existing cards below both the Cashu exclusion
area and central payment/feeding notices. Artwork is unchanged. Labels distinguish the two payment paths.

The proposed public snapshot field is `cashu`, with `version: 1`, `enabled: true`,
`id` (the prepared `lg1-` descriptor ID), `encoding` (`creqA` or `creqB`), and
`request` (public receiving instructions). This is presentation metadata only.
The initial frontend checkpoint did not include a backend producer. The later
read-only backend wiring below is now implemented and under qualification; no
production receiving descriptor has been activated. No token, seed, proof, or status capability belongs in this object.

Missing, disabled, malformed, oversized or unrenderable metadata hides the
Cashu QR without resetting financial processing. Stale snapshots cannot replace
newer metadata. Disconnect/reset clears the advertisement until a valid snapshot
restores it. Cashu and nutzap announcements retain the existing payment notice
but do not temporarily replace the Lightning QR with its Lightning animation.

The Cashu QR preserves exact payload case, uses M error correction, no logo, and
a four-module quiet zone. Its module scale is a multiple of three at 1080p to
preserve integer pixels at 720p with `fit=1`. Requests requiring more than the
384-pixel reserved QR area remain hidden. Client interoperability and real phone
scans remain unqualified; browser decoding is not evidence of sender support.

Browser fixtures come from the qualified native CDK request CLI, recorded in
`tests/website/fixtures/cashu-requests.json`, using only synthetic `.example`

results are below. Backend snapshot production, long operational descriptors and

## Read-only wallet metadata path — under qualification

Protected wallet `public_request` selection now regenerates the descriptor with
CDK and requires its ID in the accepted inventory. Its configuration checkpoint
passes [all wallet gates](cashu-public-request-config-20261116.json). The subsequent
transport change uses the existing private intake socket and its peer-UID check,
not a new daemon or public wallet control interface.

The version-1 query contains only `operation: public_request`, wallet instance,
wallet epoch, and a fresh request UUID. The reply binds all three identities and
carries either a bounded public descriptor or null. Unknown fields and stale or
mismatched registrations/UUIDs are rejected. The query never enters proof
admission, creates an acquisition or invokes a mint. Ordinary receiving disabled
or no selected descriptor returns null. Its shared protocol tests pass, including
exact-byte transport of the native-CDK short and long fixtures; full application
gates are running.

The core uses the existing intake concurrency budget and a maximum 750 ms lookup
budget. Initial, resumed and reset overlay snapshots add `cashu` metadata only
after a valid wallet reply; missing/invalid/unavailable replies yield null without
changing financial sequence or credit. `/api/v1/cashu/request` exposes the same
public instructions with no-store headers and credential-free CORS. Disabled or
unselected receiving yields 404; failed lookup yields a coarse 503; query strings
are refused. Token POST handling remains on `/api/v1/cashu`.

This metadata represents configured receiving instructions, not mint solvency or
a continuous wallet-health assertion. Positive cross-UID metadata transport and
the complete live HTTP-to-wallet-to-overlay path still need explicit fixtures.
No service, key, receiving flag, production endpoint or public announcement has
been activated by this work.

## Independent parser result — compatibility blocker found

The later [Cashu-TS 4.7.2 fixture](cashu-ts-request-initial-20261116.json)
uses exact integrity-locked upstream packages in an isolated network namespace.
It accepts both `creqB` fixtures with the expected ID, mint set, unit, reusable
flag and HTTP destination, but rejects both `creqA` fixtures with `Unsupported
amount input type`. CDK 0.18.3 serializes `amount: None` as CBOR `a:null`; this
independent parser treats a present null amount differently from an omitted
field. The generated amountless request must omit `a` before `creqA` can claim
interoperability with this client library. Browser QR decoding alone did not
catch this semantic incompatibility.

The corrective increment is prepared for the next source update after the
current metadata gates: retain CDK's typed request, omit only the null amount in
CBOR serialization, require exact typed CDK round-trip, and regenerate fixtures
through the rebuilt native CLI. The original failure evidence is preserved.
Neither parser acceptance nor this planned correction qualifies real sender
payments, repeated POST compatibility, phone scans or installed WAF behavior.
